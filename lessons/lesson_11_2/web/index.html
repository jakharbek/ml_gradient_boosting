Зачем это нужно

Поиск параметров — это много сравнений «вариант A лучше варианта B?». Каждое сравнение шумное, а вариантов много. Нужно две вещи: надёжная оценка одного варианта и разумный способ выбирать, какие варианты пробовать.

Оценка варианта: кросс-валидация

K-кратная кросс-валидация: данные делятся на $K$ частей (фолдов), модель обучается $K$ раз, каждый раз оценивается на одной части и обучается на остальных; оценка — среднее. Каждый объект побывает в валидации ровно один раз.

Проверка в ноутбуке урока: каждую конфигурацию оценили десятью разными разбиениями 80/20 и десятью разными 5-кратными CV.

4 листа1.155 ± 0.0291.177 ± 0.008

Оценка CV в 3–6 раз стабильнее. С одним разбиением разница между конфигурациями (≈ 0.1) лишь вдвое больше разброса самой оценки — неудачное разбиение могло бы её исказить. Цена — $K$ обучений вместо одного.

Ранняя остановка внутри CV

Число деревьев подбирают на каждом фолде по его валидационной части. Для итоговой модели на всех данных берут среднее число деревьев по фолдам (или чуть больше — данных стало больше).

Вложенная CV

Если CV использовалась для выбора параметров, её оценка у лучшего варианта оптимистична: из многих вариантов мы выбрали тот, которому повезло. Честная оценка всей процедуры — внешняя CV, внутри каждого фолда которой идёт свой поиск параметров (упражнение 1). Проще: отложенный тест, на который смотрят один раз.

Правильное разбиение

Для классов — стратификация (StratifiedKFold), для групп (несколько строк одного клиента) — GroupKFold, для времени — только «прошлое → будущее» (TimeSeriesSplit). Иначе оценка заглядывает в данные, которых при эксплуатации не будет.

Сетка против случайного поиска

Мы заранее посчитали ошибку LightGBM в 528 точках: 11 значений num_leaves × 8 значений colsample_bytree × 6 значений subsample (скрипт examples/search_grid.py). Теперь можно сколько угодно раз «запускать» разные стратегии поиска на этой поверхности и сравнивать их с одинаковым бюджетом.

Почему случайный поиск выигрывает (Бергстра и Бенжио, 2012)? На этой поверхности важен в основном один параметр: лучшая ошибка по значениям num_leaves меняется от 1.13 до 1.73, а по subsample — только от 1.129 до 1.152. Сетка из 27 точек проверяет всего 3 значения важного параметра и тратит бюджет на повторы по неважным. 27 случайных точек дают до 27 разных значений каждого параметра. В ноутбуке случайный поиск оказался лучше сетки с вероятностью 0.9995, 0.997 и 0.987 при бюджетах 8, 27 и 64.

Байесовский поиск: TPE в Optuna

Случайный поиск не учится на своих результатах. TPE (Tree-structured Parzen Estimator), сэмплер Optuna по умолчанию, делит уже проверенные точки на «хорошие» и «плохие» и строит для каждой группы оценку плотности $\ell(x)$ и $g(x)$. Следующую точку он выбирает там, где отношение $\ell(x)/g(x)$ велико, то есть где хорошие результаты вероятнее.

Пространство поиска

trial.suggest_int("num_leaves", 2, 128, log=True), suggest_float("learning_rate", 0.01, 0.3, log=True). Логарифмическая шкала — для параметров, у которых важен порядок величины (темп, штрафы, размер листьев).

Что дал TPE

Шесть параметров LightGBM, 40 запусков, три повтора (ноутбук). Первые 10 запусков TPE случайные, поэтому до 10 результаты совпали (1.1545). Дальше TPE ушёл вперёд: 1.1497 после 20 и 1.1422 после 40 запусков против 1.1545 у случайного поиска. Выигрыш реальный, но скромный. Главное всё равно сделала ранняя остановка и разумное пространство поиска.

Отсечение (pruning)

Запуск отчитывается промежуточной ошибкой (trial.report), и MedianPruner прекращает его, если он хуже медианы прошлых запусков на том же шаге. В примере ноутбука из 30 запусков 22 были остановлены досрочно — поиск стал в разы дешевле.

В коде

Optuna в браузерной сборке Python нет, поэтому код — для Jupyter (полная версия — в ноутбуке урока).

import optuna, lightgbm as lgb, numpy as np

def objective(trial):
    params = dict(
        num_leaves=trial.suggest_int("num_leaves", 2, 128, log=True),
        learning_rate=trial.suggest_float("learning_rate", 0.01, 0.3, log=True),
        colsample_bytree=trial.suggest_float("colsample_bytree", 0.3, 1.0),
        min_child_samples=trial.suggest_int("min_child_samples", 2, 100, log=True),
    )
    model = lgb.LGBMRegressor(n_estimators=5000, verbose=-1, **params)
    model.fit(X_tr, y_tr, eval_X=(X_val,), eval_y=(y_val,), callbacks=[lgb.early_stopping(50, verbose=False)])
    return np.sqrt(min(model.evals_result_["valid_0"]["l2"]))

study = optuna.create_study(sampler=optuna.samplers.TPESampler(seed=0))
study.optimize(objective, n_trials=40)
print(study.best_params, study.best_value)

Итоги

  1. Кросс-валидация даёт в разы более стабильную оценку, чем одно разбиение; для честной оценки после поиска нужен отложенный тест или вложенная CV.
  2. Случайный поиск эффективнее сетки, когда важны не все параметры, — а так почти всегда.
  3. TPE учится на прошлых запусках и после первых случайных обычно немного обгоняет случайный поиск; отсечение экономит время.
